# 设备异常记录关联台

KTV 门店设备异常（啸叫、画面中断、点歌延迟、离线等）的记录与自动关联系统。
店员用大白话记录现象，系统按 **包厢 / 设备 / 发生时间** 自动关联重复事件，
研判是**单台故障、包厢本地问题、区域链路故障还是公共服务故障**，并在设备拓扑上高亮故障路径。

## 运行

```bash
python3 server.py          # 默认 8000 端口
# 打开 http://localhost:8000
```

零第三方依赖（Python 3 标准库 + sqlite3）。首次运行自动建库和拓扑，
页面右上角「载入演示数据」可一键生成 18 条记录 / 8 个典型关联簇。

## 四个页面

| 页面 | 功能 |
|---|---|
| ① 店员上报 | 选包厢/设备、现象、严重度，填大白话描述；提交即自动关联并提示归并依据；右侧显示最新 30 条 |
| ② 历史记录 | 包厢/设备/现象/严重度/发生时间区间六条件组合筛选 + 分页（20/50/100 每页）+ 一键清空；结果含归并簇与研判，可直接点开簇详情 |
| ③ 关联看板 | 异常簇卡片墙，颜色区分研判类型，显示记录数/包厢数/设备数/置信度 |
| ④ 故障链路总览 | SVG 全量拓扑（服务器→核心→区域交换机→包厢设备），簇维度高亮疑似节点与故障路径 |
| ⑤ 规则与审计 | 调三个时间窗与阈值、查看归并屏障、全部自动/人工操作审计 |

簇详情抽屉内含：研判结论与理由、疑似设备、**每条记录的归并依据（规则/相似度分/时间差/参照事件）**、
归并时间线，以及拆分 / 锁定 / 关闭操作。

## 核心设计

### 1. 相似事件归并（三规则，均要求标准症状相同）

| 规则 | 场景 | 时间窗（默认） | 起评分 |
|---|---|---|---|
| **R1** 同设备 | 同一台设备复发（间歇性故障） | 60 min | 65 |
| **R2** 同包厢跨设备 | 同包厢话筒+功放都啸叫 → 包厢声学问题 | 15 min | 55 |
| **R3** 跨包厢公共链路 | 多包厢同时点歌延迟 → 点歌服务器 | 5 min | 40 |

评分 = 起评分 + 25×描述文本相似度（字符二元组 Jaccard）+ 症状关键词命中加分(10)
+ 共享上游交换机(20) + 症状有服务端疑似节点(15)；**≥ 阈值（默认60）才并入**，取最高分簇。
窗口判定是"与簇内**任意**事件"的时间差，因此乱序到达、设备 flap 都能正确归簇。

### 2. 时间窗口规则

三个窗口在「规则与审计」页可调；改参数后点顶栏「全量重算」应用到历史数据。
离线类跨区汇聚还有硬门槛：不共享区域交换机时需达到最少包厢数（默认3），
防止两个偶发离线被误判成核心故障。

### 3. 误合并拆分

- 簇详情中勾选"其实不是同一故障"的记录 → **拆分成新簇**
- 拆分自动在两组事件之间建立**归并屏障（merge_blocks）**：之后无论新事件还是全量重算，
  都不会再把它们自动并回（`correlation.py: is_blocked`）
- 拆错了可人工再合并，手动簇带标记并可选**锁定**，自动关联不再改动
- 全量重算尊重：手动簇、锁定簇、所有屏障（已通过测试验证）

### 4. 故障关系研判与可视化

按簇内房间/设备/区域分布 + 拓扑最近公共祖先（LCA）研判：

| 结论 | 触发条件 | 默认置信度 |
|---|---|---|
| 单台设备故障 | 全部记录同一设备；≥3 次标注间歇性复发 | 0.7 / 0.85 |
| 包厢本地问题 | 单包厢多设备（非公共链路） | 0.7 |
| 区域链路故障 | 同区域 ≥2 包厢离线等，LCA=区域交换机 | 0.9 |
| 公共服务故障 | 跨区同症状且有服务端节点（点歌延迟→点歌服务器，画面中断→媒体服务器） | 0.65 / 0.85 |
| 核心链路故障 | 跨区无服务节点，LCA=核心 | 0.55 |

拓扑页把"疑似设备 → 簇内各设备"的完整路径高亮，疑似点红色脉冲标记。

## 代码结构

```
db.py            # 建表、拓扑种子（3层：服务器/核心→区域交换机→4类包厢设备×15包厢）
correlation.py   # 核心：相似度评分、R1/R2/R3 匹配、屏障、split/merge/lock/recompute、研判 LCA
server.py        # 标准库 HTTP 服务 + REST API
static/          # index.html / style.css / app.js（原生 JS + 内联 SVG 拓扑）
data/anomaly.db  # sqlite（运行后生成）
```

## 历史记录查询

「历史记录」页支持店员按故障发生时的线索回溯某次具体故障：

- **组合条件**：包厢、设备（选包厢后自动收敛为该包厢 4 台设备，不选包厢可跨店查某类设备）、
  异常现象、严重程度、发生时间起止，条件之间是 AND
- **分页**：按发生时间倒序，每页 20/50/100 条可选；页码窗口跟随当前页，
  超界页码自动收敛到末页；返回 `total/page/pages/has_prev/has_next`
- **结果列**：时间、包厢、设备、现象、严重度、描述、店员、归并簇# + 研判结论；
  点簇号直接打开簇详情抽屉（时间线 / 拆分 / 锁定）
- 上报新记录后，已加载过的历史查询会带着当前条件自动刷新

后端 `GET /api/events` 支持参数：`room`、`device`、`symptom`、`severity`、
`time_from`、`time_to`（`YYYY-MM-DDTHH:MM`，仅给到分钟的结束时间自动补到该分钟末）、
`cluster`、`page`、`page_size`；非法枚举值/时间格式返回 400。
查询走 `room/device/(symptom,severity)/ts/cluster` 五个索引，
房间/设备/簇名批量预取（无 N+1），已用 2018 条数据验证走索引与分页正确性。

## API 摘要

```
GET  /api/meta /api/overview /api/topology?cluster=
GET  /api/events?room=&device=&symptom=&severity=&time_from=&time_to=&cluster=&page=&page_size=
POST /api/events
GET  /api/clusters?status=                   GET  /api/clusters/:id[/audit]
POST /api/clusters/:id/split | /lock | /status
POST /api/clusters/merge    POST /api/recompute
GET/PUT /api/settings        GET /api/blocks /api/audit
POST /api/seed | /api/reset
```
